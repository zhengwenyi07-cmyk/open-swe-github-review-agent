# 阶段文档规范

每个正式阶段使用一个独立目录，至少包含三份文档：

```text
docs/phases/
└── phase-XX-short-name/
    ├── PLAN.md
    ├── CONCEPTS.md
    └── RESULTS.md
```

这三份文档用于帮助项目所有者理解 AI 实际完成的工作，并在半年后或面试前恢复上下文。它们不是额外审批层，也不要求为每个小修复创建新阶段。

## `PLAN.md`：开始前的计划

阶段开始前创建，由主审核对话批准后交给分支对话执行。至少说明：

- 本阶段要回答的研究问题；
- 为什么现在做；
- 输入、输出和成功标准；
- 预计修改的模块；
- 运行命令与外部资源；
- 安全、权限和费用边界；
- 明确不做什么；
- 哪些结果会使下一阶段改变。

`PLAN.md` 是初步计划。实现过程中可以因真实发现调整，但必须在 `RESULTS.md` 解释偏差和原因。

## `CONCEPTS.md`：技术讲解

随实现同步更新，目标是让未参与编码的人理解该阶段。至少说明：

- 关键术语和背景；
- 数据流或控制流；
- 涉及的 Open SWE 官方源码路径；
- 新增或修改文件的职责；
- 核心算法、接口和状态变化；
- 重要设计选择及其替代方案；
- 安全边界和失败模式；
- 如何阅读关键代码；
- 与前一阶段的关系。

不能只罗列文件名，也不能把生成代码当作无需解释的黑箱。

## `RESULTS.md`：执行后的真实结果

阶段运行后完成，只记录实际发生的内容。至少说明：

- 最终实施范围以及与计划的差异；
- Git Commit、上游 Commit、模型和配置；
- 精确执行命令；
- 测试、指标、Token、耗时和费用；
- 代表性成功、失败、误报和漏报；
- 生成产物及必要 Hash；
- 安全和权限检查；
- 明确未执行的操作；
- 结论、局限性和对下一阶段的影响。

正常模型失败也是结果，不允许通过反复补跑或修改文字隐藏。

## 阶段目录初步规划

目录只在阶段真正开始时创建，不提前生成大量空文档：

```text
phase-01-local-diff-review/
phase-02-three-task-smoke/
phase-03-github-read-only/
phase-04-github-review-write/
phase-05-cross-model-comparison/   # 仅在前序结果证明有价值时创建
```

Phase 0 的静态准备已经由总体框架、技术复盘、当前 README 和测试记录完整覆盖，不再复制三份内容相同的历史文档。Phase 1 开始时正式采用本规范。

## 文档更新责任

- 主审核对话创建或批准 `PLAN.md`。
- 阶段分支对话实现功能并维护 `CONCEPTS.md` 草稿。
- 阶段分支返回结果后，主审核对话复核并完成 `RESULTS.md`。
- 主审核对话随后更新总体框架、项目交接和面试指南。

## 防止文档膨胀

- 一个阶段只保留上述三份核心文档；确有图表或外部依据时再增加附件。
- 小型修复直接记入当前阶段，不创建新的 phase、checkpoint 或 r01/r02/r03 文档。
- Schema、状态机和 Manifest 只在机器正确性或高风险权限确实需要时创建。
- 计划中的预期结果不能提前写入 `RESULTS.md`。
- 文档重点是解释设计、运行和结论，不追求形式数量。
